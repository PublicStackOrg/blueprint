# Migrating a Public Service from blueprint v0.3.0 to v0.4.0

`publicstack upgrade --to 0.4.0` is still a stub; follow this guide
manually for any Public Service generated from blueprint v0.3.0.

## What changed in v0.4.0

Phase 6 of `blueprint/docs/PLAN.md`. The big landing is the `deploy/`
directory — previously empty `.gitkeep` placeholders, now three working
on-ramps:

- `deploy/compose/` — single-VPS docker-compose stack with Caddy
- `deploy/k8s/` — cloud-agnostic Helm chart
- `deploy/terraform/` — per-cloud Terraform modules; AWS default,
  bare-k8s complete, gcp/hetzner/r2 as outputs-only stubs
- `deploy/HOSTING.md` — the headline doc

Plus a GHCR push step in CI and a `.gitignore` allowlist for
`.env.prod.example`.

## Migration steps

### 1. Pull the v0.4.0 deploy/ tree

The simplest path: regenerate from v0.4.0 cookiecutter into a sibling
directory and copy `deploy/` over.

```bash
publicstack new service my-ps --output-dir /tmp
cp -R /tmp/my-ps/deploy/* deploy/
```

If you've customized the existing (placeholder) `deploy/` files,
review the diff before merging.

### 2. Allowlist `.env.prod.example`

Add to `.gitignore`:

```diff
 .env
 .env.*
 !.env.example
+!.env.prod.example
```

### 3. Add the GHCR push job to CI

Append to `.github/workflows/ci.yml` (after the existing
`docker-build` job):

```yaml
  docker-push:
    name: Push service images to GHCR
    runs-on: ubuntu-latest
    needs: [docker-build]
    if: github.event_name == 'push' && github.ref == 'refs/heads/main'
    permissions:
      contents: read
      packages: write
    steps:
      - uses: actions/checkout@v4
      - uses: docker/setup-buildx-action@v3
      - name: Log in to GHCR
        uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      - name: Compute lowercase image prefix
        id: img
        run: |
          owner=$(echo "${{ github.repository_owner }}" | tr '[:upper:]' '[:lower:]')
          repo=$(echo "${{ github.event.repository.name }}" | tr '[:upper:]' '[:lower:]' | tr '-' '_')
          echo "PREFIX=${owner}/${repo}" >> "$GITHUB_OUTPUT"
      # … per-service Build + push steps; see the template ci.yml.
```

After first push to main, mark the GHCR packages public (one-time):

```bash
gh api -X PATCH /user/packages/container/<package>/visibility -f visibility=public
```

### 4. Bump `BLUEPRINT_VERSION`

```bash
echo 0.4.0 > BLUEPRINT_VERSION
```

### 5. Pick an on-ramp and try it

- **VPS:** copy `deploy/compose/.env.prod.example` to `.env.prod`
  on a fresh Ubuntu host, follow `deploy/compose/README.md`.
- **Helm:** `cd deploy/k8s && helm dep update && helm install ...`
- **AWS Terraform:** `cd deploy/terraform/environments/dev && cp
  terraform.tfvars.example terraform.tfvars`, fill in vpc_id /
  subnet_ids / cert ARN / password, `terraform init && terraform
  apply`.

`HOSTING.md` has the full walkthrough.

### 6. Re-run compliance

The v0.3.0 baseline still applies. Should still pass:

```bash
publicstack-compliance run --strict
```

Phase 6 doesn't add new compliance rules. The Terraform syntax is
checked by `terraform validate` (now a step in the per-PS compliance
job).

## What didn't change

No application code changes. main.py / config.py / dependencies.py /
adapters / contracts / Grid YAMLs are unchanged from v0.3.0. The
v0.4.0 bump is purely deployment scaffolding + the deploy/.

## Reverting

`git revert` is the path. The new files under `deploy/` are
self-contained; they don't change anything in `services/` /
`libraries/` / `grid/`.
